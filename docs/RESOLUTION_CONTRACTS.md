# Resolution builder: shared contracts (M0)

Coordinator-owned. Settled 26 October 2026 for the implementation of [RESOLUTION_BUILDER_IMPLEMENTATION_PLAN.md](../RESOLUTION_BUILDER_IMPLEMENTATION_PLAN.md). Types live in [`src/domain/resolution/model.ts`](../src/domain/resolution/model.ts); tables in [`src/server/schema.ts`](../src/server/schema.ts) and migration `0003_resolution_builder.sql`. Change a shared type only through the coordinator.

## Decisions

| Topic        | Decision                                                                                                                                                                                                                                                                                                                      |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Renderer     | `docx@9.14.0` (MIT), server-side, no network. Spike rendered in Microsoft Word for Mac: numbering, page break, header, "Page X of Y" footer, borderless signature table, Unicode all correct. Quick Look is not a faithful preview (ignores page breaks/fields).                                                              |
| Editor       | Tiptap 3 with custom nodes (field chip, condition, repeat, clause slot, signature block) plus `@tiptap/extension-table` and `@tiptap/extension-text-align`. Stored source is our own schema-v1 JSON (`BlockNode[]`), not Tiptap JSON and not HTML. Converters live in `src/components/template-editor/convert.ts`.            |
| Preview      | Browser preview renders the same `ResolvedDocument` the DOCX renderer consumes; it states that pagination is decided by Word.                                                                                                                                                                                                 |
| Persistence  | Typed JSON rows with explicit id, scope, revision and indexes (repository convention). Reviews and execution are separate `generation_records` rows; a `Ready` generation is immutable.                                                                                                                                       |
| Case model   | Resolution cases are separate linked records (`resolution_cases`), optionally linked to a W04 job. W07 is **not** added to the job union.                                                                                                                                                                                     |
| Directors    | Director relationships are read-only projections of posted officer events (`projectedFrom`). Officer-event `personId` values become `people.id` unchanged; names are not used to merge identities.                                                                                                                            |
| Capabilities | New: `manage_people`, `manage_templates`, `generate_documents`, `view_audit`, `export_audit`. Not granted by migration. `scripts/grant-resolution-capabilities.ts` applies an explicit, audited mapping. Template publication additionally requires `review_pack` and a different person from the version's author/submitter. |
| Dates        | Date-only strings `YYYY-MM-DD`; timestamps UTC ISO; displayed in Asia/Kuala_Lumpur. Numbers in answers are exact decimal strings.                                                                                                                                                                                             |
| Field ids    | `/^[a-z][a-z0-9_]{1,63}$/`, stable per template lineage. Case-scope ids are shared across clauses (one question); clause-scope ids are namespaced by the case's clause entry key. Conflicting case-scope definitions (type or option ids differ) block generation and name both clauses.                                      |
| Limits       | Template fragment ≤ 2,000 nodes, depth ≤ 12, ≤ 100 fields; ≤ 40 clauses per case; repeat ≤ 50 items; output ≤ 5 MiB; render ≤ 15 s.                                                                                                                                                                                           |

## Binding registry (allowlist)

`company.name`, `company.registrationNumber`, `company.address`, `company.incorporationDate`, `company.financialYearEnd`, `company.citation.directorAuthority`, `company.citation.memberAuthority`, `company.citation.electionAuthority`, `company.custom.<definitionId>`, `case.title`, `case.instructionDate`, `case.resolutionDate`, `case.effectiveDate`, `case.custom.<definitionId>`, `job.personName`, `job.effectiveDate`, `job.route`, `firm.name`, `today`, and `selection.<fieldId>.<name|capacity|appointedOn|ceasedOn>` for a `recordReference` question. Nothing else is accepted. BO data is never bindable.

## Shared server helpers (`src/server/resolution/shared.ts`)

- `auditChange(tx, actor, { companyId, scopeCompanyIds?, entityType, entityId, action, before, after, detail, reason, requestId })` — always inside the business transaction.
- `mutateCase(actor, caseId, expectedRevision, requestId, action, fn)` — the only write path for `resolution_cases` (both lanes use it).
- `readCase(actor, id, tx?)`.
- From `repository.ts`: `requestKey`, `prior`, `remember` for idempotent mutations elsewhere.

All mutation bodies carry `requestId` (uuid) and, for existing records, `expectedRevision`. Errors use `DomainError` → `{ error, code }` with 400/403/404/409. Routes use `endpoint()` and `requireActor()`.

## Implementation notes (27 October 2026)

The lanes refined some shapes; code and tests are authoritative. Notably: available clauses/assemblies are flat lists (`clauseVersionId`, `outputTypeIds`, `usageContexts`); assemblies for every active output type are offered so the preparer can switch; `newerVersions` items use `newerVersionId`/`newerVersion`; clause GET also returns `outputTypes`, `answers`, `signers`, `issues`; copy takes `sourceId`; `publish` takes `{ confirm: true }`; `/api/output-types` returns `{ outputTypes }`; `Issue` (in `validate.ts`) adds optional `severity`, `unit`, `fieldId`, `itemId`; `AuditEntryView` lives in `src/domain/resolution/records.ts`. Pack attachment is `POST /api/document-generations/:id` with `{ action: 'attach_to_pack', expectedJobRevision, requestId }`, handled by `attachGenerationToPack`.

## Review fixes: execution roles and live questions

New generations freeze `executionRequirements: { personId, role }[]` from the signature blocks actually rendered. Retained selections in inactive roles do not create execution requirements. Execution writes require `signerRole` (`directors`, `members`, or `certifiers`) alongside the signer, capacity and evidence; one person's separate signing roles require separate records. Older immutable generations derive requirements from their pinned assembly and frozen context/answers. Legacy evidence without a role satisfies a requirement only when that person has one required role; ambiguous evidence remains visible and requires explicit role records.

Clause GET also returns `formInput` (the authorised `CaseInput`, or null without a selection). The Questions UI uses the canonical domain `buildForm` and `validateAnswers` functions with its unsaved draft, so conditions, per-person rows and calculated values update locally. This does not persist answers or advance revisions. Server save and generation validation remain authoritative.
